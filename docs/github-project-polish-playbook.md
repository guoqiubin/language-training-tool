# GitHub 项目美化与公开发布操作流

这是一套适用于 Kiwi 及其他前端项目的可复用流程。目标是把一个能运行的项目，整理成安全、清晰、美观、可迭代、方便他人理解的 GitHub 作品集。

## 一、最终目标

每个公开项目至少应具备：

- 一个清晰的项目名称、Logo 和一句话定位。
- 一个能让访客直接体验的在线地址，或明确的本地运行方式。
- 一份面向普通访客也能看懂的 README。
- 一组真实页面截图，展示核心功能和视觉风格。
- 一份版本记录，说明项目如何持续更新。
- 明确的隐私、版权、第三方资源和使用边界。
- 可替换的内容结构，避免以后更新内容时破坏页面代码。

## 二、第一步：确认项目范围

开始整理前，先确认四件事：

1. 当前项目的真实目录和入口页面。
2. 当前线上地址和部署平台。
3. 哪些内容属于公开作品，哪些内容只能本地保留。
4. 是否存在其他相似项目，避免修改错项目。

项目范围不确定时，不要直接部署或上传。先检查页面入口、资源目录、部署项目名称和当前生产版本。

## 三、第二步：安全脱敏

公开仓库前，必须建立“公开区”和“私有区”的边界。

### 可以公开

- 页面结构、样式和通用交互。
- 不包含个人信息的示例内容。
- 通用 Logo、公开图标和已确认可使用的资源。
- 脱敏后的课程数据和演示截图。
- README、变更记录和运行说明。

### 不应公开

- 微信二维码、手机号、邮箱、家庭或工作地址。
- 真实用户信息、学员记录、兑换码、管理员密钥。
- API Key、Token、Cookie、私有环境变量。
- 未确认授权的游戏音频、人物头像和商业素材。
- 本地个人头像原图、录音、下载文件和临时输出。
- `.env`、`.vercel`、浏览器缓存和构建缓存。

### 推荐的忽略规则

根据项目实际情况维护 `.gitignore`，至少检查：

```gitignore
.env*
.vercel/
.DS_Store
work/
outputs/
*.mp3
*.wav
*.m4a
*.ogg
assets/private/
assets/avatar.jpg
assets/wechat-*
```

不要只依赖 `.gitignore`。已经进入 Git 历史的敏感信息，仍然可能被恢复；发现泄露时需要撤销密钥，并清理历史记录。

## 四、第三步：建立公开项目结构

推荐使用下面的结构，根据项目大小增减：

```text
project/
├── README.md
├── CHANGELOG.md
├── .gitignore
├── index.html
├── assets/
│   ├── screenshots/
│   ├── icons/
│   └── public/
├── content/
│   └── README.md
└── docs/
    ├── public-release.md
    ├── portfolio-showcase.md
    └── github-project-polish-playbook.md
```

内容、素材和页面逻辑尽量分离。未来新增课程、概念、场景或卡片时，优先更新数据文件，而不是复制一整套页面。

## 五、第四步：设计项目视觉识别

项目至少需要一个统一的视觉识别系统：

- 项目名称：短、易读、容易记忆。
- 一句话定位：说明它为谁解决什么问题。
- Logo：优先使用简单 SVG，避免依赖未授权图片。
- 主色：建议定义 1 个主色、1 个强调色和 1 组中性色。
- 卡片：统一圆角、边框、阴影和间距。
- 字体：中文优先保证清晰度，英文和中文保持合理比例。
- 响应式：桌面端突出内容层级，移动端保证按钮可点击、文字不重叠。

视觉美化不是单纯放大字体。应同时检查容器宽度、行高、留白、卡片边界、按钮大小和长文本换行。

## 六、第五步：完善 README

README 应让两类人都能看懂：

- 普通访客：知道这是什么、能不能体验、从哪里开始。
- 开发者：知道如何运行、如何更新、哪些内容不能提交。

推荐结构：

```md
# 项目名称

一句话定位。

## 在线体验

项目地址：...
用户指南：...

## 项目简介

解决什么问题，服务什么用户。

## 核心功能

- 功能一
- 功能二
- 功能三

## 视觉预览

插入 3–5 张真实页面截图，并配简短说明。

## 本地运行

说明最简单的启动方式。

## 内容与版本

说明内容如何新增、替换和删除。

## 安全与隐私

说明公开范围和私有资源边界。

## 许可证与第三方资源

说明项目代码、图片、音频和字体的来源及限制。
```

README 不要堆积开发术语，也不要写无法验证的宣传语。在线地址、功能状态和授权说明应以实际情况为准。

## 七、第六步：制作作品集截图

截图优先选择真实页面，而不是单独制作的宣传图。建议准备：

1. 首页：展示项目定位和入口。
2. 用户指南：展示新用户如何开始。
3. 核心训练页：展示主要学习体验。
4. 特色模块：展示专项英语、任务中心或趣玩中心等差异化功能。
5. 细节交互：展示卡片、查词、朗读或进度记录。

截图前检查：

- 页面中没有个人联系方式和真实用户数据。
- 页面没有开发者工具、浏览器标签隐私信息或调试提示。
- 截图宽度统一，建议桌面端使用 1200px 左右。
- 截图文件名清晰，例如 `training-center.gif`、`guide-preview.gif`。
- 每张截图在 README 中有一句说明。
- 不要为了展示而伪造不存在的功能。

## 八、第七步：加入用户指南

面向普通用户的项目，建议单独提供 `guide.html` 或站内说明页，至少解释：

- 这个项目适合谁。
- 应该从哪个入口开始。
- 难度等级如何选择。
- 每个主要模块是做什么的。
- 朗读、查词、进度保存等功能如何使用。
- 遇到问题时应该怎么处理。

用户指南应从“第一次打开网站的人”出发，而不是从开发者角度写。

## 九、第八步：建立可迭代的内容机制

内容更新建议遵循以下原则：

- 每条内容有稳定 ID，不要只依赖数组下标。
- 内容和页面组件分离。
- 新增内容不改变旧内容的 ID。
- 删除内容前记录原因，必要时保留迁移映射。
- 每次更新记录在 `CHANGELOG.md`。
- 大版本变化时更新 README 的功能说明。
- 私有素材和公开素材分目录管理。

推荐记录格式：

```md
## v1.1.0 · 2026-11-03

- 新增用户指南。
- 增加训练中心和专项英语展示截图。
- 优化桌面端卡片间距。
- 未改变已有内容 ID。
```

## 十、发布前复核清单

### 安全

- [ ] 没有密钥、Token、Cookie 和私有环境变量。
- [ ] 没有个人二维码、手机号和真实用户数据。
- [ ] 本地音频、个人头像和临时文件已排除。
- [ ] 第三方图片、图标、字体和音频来源已记录。

### 美观

- [ ] 首页、用户指南和核心页面视觉一致。
- [ ] 中文字体清晰，桌面端没有拥挤和重叠。
- [ ] 卡片边界、层级、留白和按钮状态清楚。
- [ ] 移动端至少检查一次，保证基本可用。

### 可用

- [ ] 在线地址可以访问。
- [ ] README 中的链接有效。
- [ ] 用户指南入口可见。
- [ ] 核心按钮和主要导航可以正常工作。
- [ ] 代码语法检查和基础页面检查通过。

### 可迭代

- [ ] 有 `CHANGELOG.md`。
- [ ] 有内容目录说明。
- [ ] 新增和删除内容的规则明确。
- [ ] 公开代码和私有资源边界明确。

## 十一、每次版本更新的固定操作流

1. 先确认目标项目和当前线上版本。
2. 读取现有 README、CHANGELOG 和公开边界说明。
3. 只修改本次明确范围内的内容。
4. 更新页面、截图、README 和版本记录。
5. 扫描敏感信息和私有资源。
6. 检查桌面端与移动端布局。
7. 做语法检查和页面访问检查。
8. 发布到预览环境或生产环境。
9. 打开真实页面复核关键路径。
10. 向项目负责人说明已完成内容、验证范围和仍未验证的部分。

## 十二、交给其他项目使用时的提示词模板

可以把下面这段作为其他项目的固定任务说明：

> 请将本项目整理成适合公开展示的 GitHub 作品集。先确认项目范围和线上入口，再完成安全脱敏、公开目录整理、统一视觉识别、README、用户指南、版本记录和真实页面截图。禁止公开密钥、个人联系方式、用户数据、私有音频和未确认授权的素材。所有页面需要兼顾桌面端与移动端，不得出现文字重叠。内容应与页面逻辑分离，便于未来新增、替换和删除。完成后请列出修改内容、验证结果、未验证范围，以及是否真正上传了 GitHub。

## 十三、交付时必须说明

每次完成后，最终说明至少包含：

- 已修改哪些文件和功能。
- 在线地址是否已更新。
- 截图是否真实生成。
- 安全扫描做到了什么范围。
- 桌面端和移动端检查到了什么程度。
- 是否已经上传 GitHub；如果没有，说明缺少什么授权或仓库信息。

这能避免把“本地整理完成”“网站已发布”和“GitHub 已上传”混为一谈。
